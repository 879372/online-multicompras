# Cell Phone Store — Backend Project Spec

## Overview

Backend system for a small cell phone store. It powers two consumers:

1. A **public product catalog** (consumed by a separate React/Vite frontend)
2. A **WhatsApp bot** (built in n8n) that queries product data via HTTP instead of querying the database directly

The store owner manages products manually through the Django Admin. Product/price updates that arrive from a supplier via WhatsApp text are extracted by an LLM (outside this backend, in n8n) and sent here as **pending approvals** — the owner approves them before they go live.

This is a **single-tenant, closed project** for one client. No multi-tenancy, no SaaS features, no tenant isolation logic.

## Tech stack

- **Language/framework**: Python 3.12, Django 5.x, Django REST Framework (DRF)
- **Database**: PostgreSQL
- **Auth**: JWT (djangorestframework-simplejwt)
- **Hosting target**: Railway (keep settings.py compatible with environment variables for DB connection, `DATABASE_URL` style)
- **API docs**: drf-spectacular or drf-yasg for auto-generated Swagger/OpenAPI docs

## Scope for this phase

Build **only the backend**: models, migrations, admin registration, serializers, viewsets/endpoints, auth, and permissions. No frontend, no n8n workflow work.

## Apps structure

Create a Django project named `store_backend` with these apps:

- `accounts` — custom user model and auth
- `catalog` — products and pending approvals
- `conversations` — WhatsApp conversation/handoff log

## Data models

### accounts.User

Extend Django's `AbstractUser`. Only one role matters for now: **owner/staff** (use Django's built-in `is_staff`/`is_superuser`, no custom role field needed — keep this simple, this is not a multi-role system).

Fields: standard Django user fields are enough (`username`, `email`, `password`, `is_staff`, `is_superuser`, `is_active`).

### catalog.Product

| Field | Type | Notes |
|---|---|---|
| `id` | AutoField (PK) | |
| `name` | CharField(255) | |
| `category` | CharField(100) | e.g. "phone", "accessory" |
| `price` | DecimalField(10,2) | |
| `stock` | PositiveIntegerField | default 0 |
| `description` | TextField | blank=True |
| `image` | ImageField or URLField | nullable, store either upload or external URL — pick URLField for simplicity unless told otherwise |
| `is_active` | BooleanField | default True. Inactive products are hidden from the public catalog but not deleted |
| `created_at` | DateTimeField | auto_now_add |
| `updated_at` | DateTimeField | auto_now |

Register in Django Admin with list_display showing name, category, price, stock, is_active, and list_filter on category/is_active. Make it easy for a non-technical owner to edit inline.

### catalog.PendingUpdate

Represents a price/product change extracted from a supplier message, awaiting owner approval.

| Field | Type | Notes |
|---|---|---|
| `id` | AutoField (PK) | |
| `product` | ForeignKey(Product, null=True, blank=True) | null if this is a brand-new product, not an update to an existing one |
| `proposed_name` | CharField(255) | used when product is null (new product) |
| `proposed_price` | DecimalField(10,2) | |
| `proposed_stock` | PositiveIntegerField | nullable |
| `raw_text` | TextField | the original supplier message text, for audit/debugging |
| `status` | CharField with choices: `pending`, `approved`, `rejected` | default `pending` |
| `created_at` | DateTimeField | auto_now_add |
| `resolved_at` | DateTimeField | nullable, set when approved/rejected |

Register in Django Admin with a custom admin action "Approve selected" that:
- If `product` is set: updates that product's `price`/`stock` from the proposed values
- If `product` is null: creates a new `Product` from the proposed fields
- Sets `status = approved` and `resolved_at = now()`

### conversations.Conversation

Simple log of WhatsApp conversations for the owner to review, especially handoffs.

| Field | Type | Notes |
|---|---|---|
| `id` | AutoField (PK) | |
| `customer_phone` | CharField(50) | |
| `status` | CharField with choices: `bot_handling`, `handoff`, `closed` | default `bot_handling` |
| `summary` | TextField | blank=True, short summary generated by the bot when handing off |
| `created_at` | DateTimeField | auto_now_add |
| `updated_at` | DateTimeField | auto_now |

Register in Django Admin, read-mostly (owner reviews, doesn't need to edit much).

## API endpoints (DRF)

Use DRF viewsets + routers where sensible. Auth via JWT (`djangorestframework-simplejwt`): `POST /api/auth/token/` and `POST /api/auth/token/refresh/`.

### Public (no auth) — consumed by the React catalog and the n8n bot

- `GET /api/catalog/products/` — list active products only. Support `?search=` (name icontains) and `?category=` filters.
- `GET /api/catalog/products/{id}/` — retrieve one active product.

### Authenticated (owner only, `IsAuthenticated` + `IsAdminUser` or `is_staff` check) — used by n8n with a service account/token, and optionally an admin panel later

- `GET /api/catalog/pending-updates/` — list pending updates, filterable by `?status=pending`.
- `POST /api/catalog/pending-updates/` — create a pending update (this is what n8n calls after the LLM extracts data from the supplier's WhatsApp message).
- `POST /api/catalog/pending-updates/{id}/approve/` — custom action, applies the update to the product (create or update) and marks it approved.
- `POST /api/catalog/pending-updates/{id}/reject/` — custom action, marks it rejected.
- `GET/POST /api/conversations/` — list/create conversation logs (n8n posts here on handoff).
- `PATCH /api/conversations/{id}/` — update status (e.g. mark `closed`).

## Permissions summary

- Public product endpoints: `AllowAny`, read-only, filtered to `is_active=True`.
- Everything else: `IsAuthenticated`. No need for granular roles — single owner user is enough for this project.

## Non-functional requirements

- Use environment variables for all secrets and DB config (`SECRET_KEY`, `DATABASE_URL`, `DEBUG`, `ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS`).
- Enable `django-cors-headers`, configured to allow the React frontend's origin and n8n's origin.
- Add `django-environ` or `python-decouple` for env var handling.
- Include a `requirements.txt`.
- Include Django Admin properly configured and usable out of the box (this is the owner's primary interface for now).
- Write basic model-level docstrings/comments explaining the approval workflow, since a future developer (or the AI itself in a later session) needs to understand why `PendingUpdate` exists.

## Explicitly out of scope for this phase

- No multi-tenancy / tenant_id anywhere.
- No frontend code.
- No n8n workflow changes.
- No payment processing.
- No customer accounts/login — customers never authenticate, they only interact via WhatsApp.
